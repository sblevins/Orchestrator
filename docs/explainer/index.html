The current implementation is a local Python/SQLite supervisor with native Claude Code and Pi frontends. It saves project state, runs independent planning and criticism, and supervises a slow background monitor. It is not a Temporal deployment or a third-party Pi orchestration plugin.

Worker routing and worker execution are enabled, with no worker model defaults. Ask the coordinator to draft, update, or repair .orchestrator/crew-dispatch.json with repeatable setup_project calls using worker preferences you choose. An ordinary routing policy file is control metadata: untracked, tracked, or staged policy-only changes do not block write-worker preparation; unrelated source changes still do. Missing or invalid policy blocks dispatch; saving policy does not launch, approve, or accept work.

Plain version: the quick model talks with you, stronger models design and check the work, and software remembers the jobs. Workers prepare candidates; checked acceptance uses an authorized decision or standing project authorization.

1. Open the native frontend

From the cloned repository, run either native interface:

cd /path/to/Orchestrator
claude
# Or:
pi

On first use, approve native project trust and the local Orchestrator integration when prompted. The repository hooks or extension initialize the coordinator; no separate launcher is required. Tell it which project to work on and the project's existing directory.

Requirements: Linux, Python 3.11+, machine-resources, authenticated Claude Code and Pi SDK 0.99.2 for the default specialist roles, including Pi's openai-codex provider for the critic. No Python runtime dependencies need installing.

Native model precedence matters. Pi selects the configured orchestrator role automatically. Native Claude respects its own CLI and settings precedence, so a global wrapper or model pin can override the repository's Sonnet/low foreground preference. Use Claude's /model and /effort, or the optional bin/orchestrator start launcher, to apply your desired foreground settings. Background roles use Orchestrator's merged project configuration. Use project_settings and repeatable configure_project calls to save settings and project-local planning.templates in private <home>/config/projects/<bound-id>.json, never another project or shared settings. Select a template with planning.workflow; shared home workflow files are administrator-only customization.

Plain version: starting Claude normally may keep the model you already chose for Claude. That does not change which models this project uses for background planning and checking.

See frontend setup and the repository guide for project registration, observer mode, and takeover.

See configuration for the supported fields.

Guarded workers have file tools, plus a sandboxed run_command when commands.enabled = true; commands.sandbox = false runs those commands on the host. execution.mode = "trusted" enables native foreground tools and owned worker run_command for commands and tests. Trusted commands are not an operating-system sandbox and can act outside file-tool path restrictions. execution.base_ref selects the Git branch for worker checkouts, not a directory. Pi reuses the canonical auth path without inherited plugins, skills, or project settings. Quota-dependent candidate arrays and floors fail closed because a supported quota evidence adapter is unavailable. Plain version: if required quota information cannot be checked, no worker is chosen from that policy.

Four roles for planning, two ongoing roles

Clarify material unknowns before a paid planner call, then obtain independent final review. retry_review retries an eligible failed critic using the saved draft without rerunning the planner; unknown outcomes are not blindly replayed. The planner and critic run as temporary specialists during planning and substantial replanning. The fast orchestrator and slow monitor remain the ongoing roles. The monitor is an event-driven role, not a model continuously generating text.

Every user prompt is saved for review. Exact routine status questions do not wake an expensive monitor call, but ambiguous or consequential requests do. The orchestrator can request extra scrutiny; it cannot veto the program's required reviews. The monitor waits for foreground completion and monitoring.quiet_seconds, 20 by default. Only blocking monitor findings interject; informational and warning findings remain silent.

Plain version: you can ask for progress without starting another deep review. Important new requests are saved and checked in the background.

Why split the roles?

The orchestrator still needs reliable tool use and delegation, even when another model does the planning. An independent critic needs the original request and evidence, not just the planner's persuasive summary. Different providers can still make the same factual mistake.

Plain version: choosing the right job matters as much as doing it. A second model checks the work, but its answer still needs evidence.

Public speed rankings do not measure time to a useful answer and correct dispatch in this project. Live model/effort acceptance, latency, monitoring quality, and costs still need workload-specific evaluation.

5. What “does not lose track” means here

  • Save task intent and durable events; identify attempts and actual processes before accepting results.
  • Keep notifications until explicitly acknowledged, and redeliver after reconnect.
  • Validate dependency graphs and apply live project permissions, with explicit authorized decisions through bound conversational APIs or optional operator CLI.
  • Separate private project knowledge from live runtime state; use revision checks when changing notes.
  • Apply deadlines, cancellation, bounded review rounds and machine resource reservations outside the model.
  • Reconcile unfinished work after restart, preserving uncertainty instead of silently replaying it.

Plain version: closing the chat does not erase the job list. When a result is uncertain, the program says so instead of pretending the job finished or starting it twice.

Limits that matter

The supervisor can outlive the frontend, but no boot service is installed. After a supervisor crash or reboot, it must be started again; binding or resuming a project starts it. Read-only harness settings are not protection against hostile programs sharing the same operating-system account.

Offline tests exercise real subprocesses with fake model harnesses, graph constraints, session reconnection and recovery boundaries. They do not establish paid model access, answer quality, native microphone behavior, or live Claude idle wakeup. Harness-reported costs are not verified per-turn spending totals.

Project permission defaults are coordinator_approvals=true, require_write_approval=false, and enforce_monitor_holds=true. Change them conversationally with configure_project; current project permissions remain live controls. Authorized decisions use bound approve_plan, resolve_hold, approve_worker, accept_worker, and approve_node APIs, or the optional operator CLI. Plan approval still requires independent review and fresh monitor evidence; routing rules may require explicit write approval even when the project default does not. A successful worker produces a candidate, not an accepted graph result. Checked acceptance unlocks dependent work; only a comparison team's parent request can be accepted, and nothing automatically merges into the source branch or pushes. execution.unattended = true supplies standing project authorization to approve reviewed plans and accept candidates with an explicit empty remaining_issues list and satisfied live gates. Explicit worker approval required by policy, including security-audit teams, is still required. Plain version: you can authorize routine progress in advance, but unresolved problems and required worker approval still stop it.

Explicit image generation uses the separately billed OpenAI Images API with OPENAI_API_KEY, not subscription OAuth. Project images.enabled defaults to false; supported outputs are PNG and JPEG. Plain version: images need separate permission and an API key, and they cost extra.

These helper integrations are undergoing offline validation; paid provider access has not been verified, and the running deployment has not yet been activated on these changes.

Evidence and evaluation checklist

Evaluate the exact harness, model, effort and tool combination together. Measure first useful response, valid delegation, plan and critique quality, missed decisions, monitor delay, stale-result handling and cost per accepted outcome.

Fault tests should cover crashed processes, duplicate or missing notifications, out-of-order results, cancelled work, changed plans, stale approvals and simultaneous projects. A heartbeat means a process is alive, not that its work is useful.

Plain version: test both whether the models do good work and whether the program keeps accurate records when something breaks.
